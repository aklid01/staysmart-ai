# Architectural decisions

Decisions are recorded with their rationale. A decision that refers to a component not built yet is marked as a decision only, not an implemented capability.

| # | Decision | Rationale | Status |
| --- | --- | --- | --- |
| 1 | uv with `pyproject.toml`, `uv.lock` and a pinned `.python-version` | This machine has several Python 3.13 interpreters and `pip` targets a different one than `python`. A project virtual environment via `uv sync` and `uv run` removes ambiguity and makes setup reproducible. | Implemented |
| 2 | Official MCP Python SDK pinned to 2.x (`mcp>=2.3,<3`) | 2.x is the current stable line. It replaces v1 `FastMCP` with `MCPServer` and adds a first-class `Client`. Most tutorials show v1, so the version is pinned explicitly and verified with a smoke import before any MCP code exists. | Implemented (2.3.0 installed and import-verified) |
| 3 | Starlette, not FastAPI | Required by the project brief. The MCP SDK also depends on Starlette, so no extra web framework is needed. | Implemented (Phase 3) |
| 4 | In-process `HotelProvider` Protocol instead of a separate mock REST service | The brief asks for a replaceable local provider and forbids microservices without demonstrated need. A second HTTP process would add failure modes and setup cost without educational value. A real REST provider can later implement the same Protocol. | Implemented |
| 5 | Versioned JSON dataset with deterministic date-aware inventory | Supports realistic check-in and check-out validation, multi-night totals, sold-out nights and partial availability, while keeping tests deterministic without a database. | Implemented |
| 6 | `hashlib.sha256` seeding and a fixed anchor date | Avoids Python's randomized `hash()` and any `datetime.now()` dependence, so the same query always produces the same result and the E2E artifact is reproducible. | Implemented |
| 7 | Provider exposes three operations only | `compare_hotels` and `get_hotel_policies` are derivations over raw facts. Keeping them in a service layer preserves provider replaceability and keeps MCP tool schemas independent of the data source. | Implemented (service layer is Phase 2) |
| 8 | Configurable currency with a USD default dataset | International sample destinations; currency remains explicit on every monetary field and configurable through `STAYSMART_CURRENCY`. A mismatch between settings, query and dataset raises `CurrencyMismatchError`. | Implemented |
| 9 | Spec-first tests and a reproducible E2E artifact | Project rules require tests before implementation and E2E tests with a checkable artifact. `tests/phase1/CONTRACT.md` and the tests were written while the implementation modules did not exist, and the golden file is authored from the contract rather than generated by the implementation. | Implemented |
| 10 | No formatter or linter configured | Project rules require asking permission before configuring formatting tools. Revisit in Phase 7. | Implemented |
| 11 | `fastembed` and `openai` are declared when their phases need them | FastEmbed depends on onnxruntime and tokenizers, which can lag new Python versions. Deferring these dependencies kept the Phase 0 lock resolvable; both were added in their phases after verifying Python 3.13 compatibility (fastembed in Phase 4, openai in Phase 5). | Implemented |
| 12 | Exactly the seven documentation files named in the brief | Keeps the documentation surface small and avoids describing features that do not exist. Unimplemented documents carry explicit status stubs. | Implemented |
| 13 | Sold-out is a result state, not an exception | A `SoldOutError` would be dead code: callers need the sold-out dates and partial-availability flags to explain recommendations. `available=False` plus `sold_out_dates` is more useful and avoids a misleading exception. This replaces the earlier plan's unused `SoldOutError`. | Implemented |
| 14 | `get_hotel_details` accepts optional dates and defaults to one night at the dataset anchor date | Quotes require a date range, but the operation should remain callable with just a hotel id. The anchor default is fixed and documented, so no wall-clock value leaks into results. | Implemented |
| 15 | `STAYSMART_WINDOW_DAYS` caps the dataset horizon via `min(dataset.window_days, settings.window_days)` | Gives the setting a real purpose without duplicating the dataset's own window, and lets an operator shorten the bookable horizon deterministically. | Implemented |
| 16 | Nightly rates for a partial stay cover available nights only, and `total_price` is `null` | Prevents an invented total from being read as a verified price. `sold_out_dates` disambiguates which nights are missing. | Implemented |
| 17 | The E2E snapshot normalizes CRLF before byte comparison | Git on Windows may check out the golden file with CRLF. Normalizing both sides keeps the check reproducible without adding a `.gitattributes` file. The test also asserts semantic values independently, so it is not a change detector. | Implemented |
| 18 | `pytest-asyncio` auto mode with an explicit fixture loop scope | Reflects the async provider interface and removes a deprecation warning from the test run. | Implemented |
| 19 | MCP SDK 2.x `MCPServer`/`Client` API, verified against the installed 2.3.0 package source | Most tutorials show the v1 `FastMCP` API. The v2 server registers tools from type-hinted signatures, validates arguments with pydantic, and returns structured content for pydantic model results. Phase 2 read the installed SDK before coding and the contract pins the observable behavior. | Implemented |
| 20 | Anticipated tool failures raise `ToolError`, and the client-visible text carries the SDK prefix `Error executing tool <name>: <message>` | The SDK wraps anticipated failures with that prefix and reduces unexpected crashes to a generic message, so internal details never leak to a model. Tests and the golden artifact pin the full prefixed text. | Implemented |
| 21 | `compare_hotels` and `get_hotel_policies` are service-layer derivations over the `HotelProvider` Protocol | Implements decision 7. The provider stays three raw operations; derivations compose details calls, so a real connectivity provider needs no comparison endpoint for the MCP tools to work. | Implemented |
| 22 | Comparison reports unknown ids in `unresolved_hotel_ids` instead of failing the whole call | One bad id should not destroy a six-hotel comparison; a success result with empty rows plus unresolved ids is honest and lets an agent recover by dropping the bad id. | Implemented |
| 23 | Tools never accept a currency argument; the server pins currency from `Settings` | Currency is a deployment property, not a per-call choice. This removes a whole class of invalid arguments; a settings/dataset mismatch still fails at provider construction. | Implemented |
| 24 | stdio entrypoint is `python -m staysmart.mcp_server`; all logging goes to stderr | The stdio protocol owns stdout. Keeping the `staysmart` logger on stderr (Python's default handler) leaves the protocol channel clean; the subprocess E2E test passing is the standing proof. | Implemented |
| 25 | Tests exercise the server through an in-process MCP client and a real stdio subprocess | The in-process `Client(server=MCPServer_instance)` exercises the full protocol handler stack cheaply; one subprocess test proves the actual transport, handshake and clean shutdown. Both avoid paid credentials. | Implemented |
| 26 | `HotelComparison` was extended in place rather than replaced | Phase 1 left it as scaffolding. Adding `unresolved_hotel_ids`, stay context and mock markers keeps the Phase 1 type name stable for later phases and the UI. | Implemented |
| 27 | `search_hotels` validates stay dates before constructing the query | The pydantic query validator would otherwise raise a raw `ValidationError` inside the tool, which the SDK reports as a crash. An explicit check maps it to `InvalidDateError` with a clean message (`check_out must be after check_in`) that an LLM can act on. | Implemented |
| 28 | The Starlette app connects to the MCP server as a stdio subprocess, not in-process | The documented architecture separates MCP communication from the HTTP interface; a real subprocess proves the same server binary an external MCP client would use, keeps tool execution out of the web process, and reuses the Phase 2-tested launch pattern. Tests inject an `InProcessMcpConnector` for speed, and one transport test plus the demo artifact exercise real stdio. | Implemented |
| 29 | One long-lived MCP session managed in the Starlette lifespan | The connector is entered once at startup and closed at shutdown, so requests share a warm session instead of paying subprocess spawn cost per call. The connector is injectable, so tests never depend on process lifecycle. A session failure mid-request maps to 503 `mcp_unavailable`. | Implemented |
| 30 | Tool failures are classified by provider message fragments, with a 502 fallback | The SDK reports tool failures as `is_error=True` plus text only; codes do not survive the transport. Matching the stable, Phase 2-pinned message fragments (`No destination matches`, `Unknown hotel_id`, date-window texts) recovers useful 404/400 semantics without changing the Phase 2 contract. Anything unrecognized, including generic crash texts, becomes 502 `tool_error` with the raw message. MVP trade-off: the classifier is centralized in `src/staysmart/app/errors.py` and the fragments are pinned by tests. | Implemented |
| 31 | Request models mirror the tool inputs, with `extra="forbid"` and `ge=1` guests/rooms | One schema per operation, mirroring the MCP tool inputs 1:1 (no currency field), keeps the HTTP contract honest and the frontend predictable. Strictness catches frontend typos as 422 instead of silently ignoring fields. The tool schemas leave guests/rooms unconstrained, so the HTTP layer adds positivity to reject nonsensical parties early; semantic date validation deliberately stays with the tools so rules have one source of truth. | Implemented |
| 32 | `POST /api/chat` is a validated 501 stub in Phase 3 | The endpoint and its `ChatRequest` schema (message, conversation_id, history) exist and are tested, so the frontend contract and the agent seam are proven early. Returning `agent_not_available` instead of a keyword router avoids building throwaway parsing logic that the Phase 5 LLM agent would replace, and avoids implying chat works. | Implemented |
| 33 | Structured hotel endpoints ship alongside the chat stub | The Phase 6 frontend needs direct data paths for cards, details, comparison and policy views that do not depend on the LLM. Exposing the five tools over HTTP also proves the app-to-MCP plumbing end to end before the agent exists. `/api/health` pings `list_tools()` so connectivity is observable. | Implemented |
| 34 | CORS is configured now with origins from `STAYSMART_CORS_ORIGINS` | The Phase 6 Vite dev server calls the API from a browser, so preflights will start failing the day the frontend exists unless the API already answers them. Defaults target the Vite dev origins; methods are limited to GET and POST. | Implemented |
| 35 | `httpx` joins the dev group for endpoint tests; no streaming | Starlette's `TestClient` requires httpx, and the sync context-manager form runs the lifespan so the MCP session is live during requests. Responses are plain JSON; SSE/streaming adds complexity the brief does not ask for. | Implemented |
| 36 | The RAG knowledge base is an authored corpus, not an online dataset | No public dataset provides hotel policy/FAQ/reference text per hotel (searched: review corpora, booking CSVs, OTA scrapes, MFAQ). External content would need rewriting to match the mock dataset's facts anyway, and the honesty invariants require documents guaranteed free of prices and availability. The 53 authored documents in `data/knowledge/v1/` are license-clean and fact-pinned to the dataset by tests. | Implemented |
| 37 | RAG retrieval is a Python service, not an MCP tool or HTTP endpoint | The brief fixes the MCP tool set at five and the HTTP contract at the chat/health/hotel surface. The Phase 5 agent consumes `RagRetriever` directly; exposing retrieval earlier would add an unused surface and blur the "retrieval is separate from structured search" invariant. | Implemented |
| 38 | FastEmbed `BAAI/bge-small-en-v1.5` with a plain numpy cosine index | bge-small is small, free, English-tuned, and verified installable on Python 3.13 before implementation. With roughly 170 chunks, brute-force cosine over a unit-normalized matrix is instant; a vector database would violate the no-unneeded-infrastructure rule. Persistence is `vectors.npy` plus `chunks.json`, gitignored as a generated artifact. | Implemented |
| 39 | Hotel chunks are enriched with the destination resolved from the dataset | Destination filtering must be able to return hotel documents (a Vancouver question should find Vancouver hotels), but hotel docs only carry `hotel_id` in their frontmatter. Ingestion resolves the mapping once from the dataset; the corpus frontmatter stays honest to its own document type. | Implemented |
| 40 | Tests run offline with a deterministic stub embedder; the real model is exercised by the demo snapshot | Embedding logic must not require a model download, so a hash-based `DeterministicEmbedder` covers chunking, filtering, ranking and context assembly. `scripts/demo_rag.py` and its snapshot test exercise the real FastEmbed path; the model is a free one-time download, so no paid credentials are involved. Scores are rounded to 4 decimals for stable artifacts. | Implemented |
| 41 | Knowledge documents may state check-in and check-out times | The provider honestly reports these as `information_gaps`; the destination guides are the legitimate document source for them. This gives Phase 5 a real demonstration of combining structured gaps with retrieved context, without contradicting the provider. | Implemented |
| 42 | The agent speaks OpenAI function calling through the official `openai` SDK, not hand-rolled HTTP | The brief requires configurable OpenAI-compatible endpoints; the async SDK handles streaming-less chat completions, tool-call parsing and retries against any compliant server. The local endpoint (`LLM_BASE_URL`, default `http://127.0.0.1:3425/v1`) serves tool-capable models and needs no key, so `LLM_API_KEY` defaults to empty. Model choice stays in settings, never in agent logic. | Implemented |
| 43 | The agent gets the five MCP tools plus one `search_knowledge` tool | Hotel facts must come from the pinned MCP tool set (single source of truth); knowledge retrieval is exposed as a first-class tool so the model decides when descriptive context is needed and which filters apply. Six tools keep the choice space small enough for reliable selection. | Implemented |
| 44 | Safeguards are structural, not prompt-only | Bounded turns (6) and tool calls (12) with forced no-tool summaries stop unbounded loops; exact-duplicate calls are rejected with feedback; tool failures become `Error:` content the model can react to; and the `hotels` array in chat responses is assembled exclusively from real tool payloads, so fabricated hotels cannot reach the frontend even if the model hallucinates. The prompt adds grounding rules, but the code enforces the load-bearing invariants. | Implemented |
| 45 | Chat responses carry structured payloads alongside text | The frontend needs cards, comparisons and citations, not just prose. `AgentTurnResult` returns `hotels` (search hits plus details), `comparison`, `sources` and `tool_trace` next to `message`, so the UI renders data views from tool-derived structures instead of parsing model text. | Implemented |
| 46 | Conversation state lives with the client | The server stores no sessions: `history` and `conversation_id` round-trip through each request. For an MVP this removes session lifecycle, expiry and consistency concerns while satisfying the brief's "support conversation context where necessary"; the schema leaves room for a server-side store later. | Implemented |
| 47 | The agent E2E artifact is verified semantically, not byte-compared | Model text is nondeterministic, so a byte-exact golden would be flaky. `artifacts/agent_demo.json` is checked with semantic assertions (tools used, mock-dataset hotel ids, source presence) and the test skips when the configured endpoint is unreachable. The deterministic provider data behind it stays byte-pinned by the phase 1-4 goldens; the offline agent tests use a scripted model and remain fully deterministic. | Implemented |
| 48 | Vite + React + TypeScript with no router, no state library, no UI framework | The brief asks for a simple, polished interface and forbids complicated UI architecture. One chat-centric view needs no routing; React hooks cover the state; hand-written CSS with design tokens keeps the dependency surface to react, react-dom and the Vite toolchain. `npm create vite` gave the scaffold. | Implemented |
| 49 | Hotel cards render from the chat response's `hotels` array, dialogs from the structured endpoints | Cards come exclusively from tool-derived payloads (search hits and details), so the UI cannot display hotels the agent did not actually retrieve. Details and policies open real GET endpoints instead of parsing model text, exercising both channels the brief requires the frontend to use. | Implemented |
| 50 | Destination gradient placeholders instead of binary images | The brief allows "images or appropriate placeholders". Deterministic CSS gradients keyed by destination with the hotel initial and city label avoid licensing questions, offline asset management and any implication that a stock photo depicts the fictional property; `data_source="mock"` stays visible on every card. | Implemented |
| 51 | Markdown-lite chat rendering (paragraphs, bold, inline code, pipe tables) | The grounded answers contain markdown headings, bold and pipe tables. Rendering paragraphs, bold, inline code and simple pipe tables covers the model's actual output without pulling a markdown engine; the comparison data also arrives structurally, so the chat table is a bonus, not the data path. | Implemented |
| 52 | Frontend E2E is a black-box browser session with screenshots, not pytest | The brief's test stack is pytest for the Python side; the UI is verified the way a user would drive it: real browser, real clicks and keystrokes, screenshots plus an interaction log as the reproducible artifact (`artifacts/ui_demo/`, summarized in `tests/phase6/interaction_log.json`). Deterministic backend behavior behind the UI was already byte-pinned by phases 1-5. | Implemented |
| 53 | The check-in-time prompt rule is tightened instead of adding retrieval plumbing | Phase 5 observed the model sometimes answering "confirm with the property" even when the retrieved destination guide contained the exact times. The system prompt now states explicitly that destination guides DO carry check-in/check-out times and must be quoted with a citation when retrieved. Retrieval itself was proven correct (the right chunks came back), so the fix belongs in the prompt; the result stays semantically verified because model output is nondeterministic. | Implemented |
| 54 | No auto-reconnect for a dead MCP session, and no session lock | If the stdio subprocess dies mid-session, calls fail with 503 `mcp_unavailable` and the service must be restarted; auto-reconnect would add lifecycle complexity without a demonstrated need in a single-user demo. No interleave corruption was observed on the shared session, so a serialization lock was not added either; both choices are recorded so the trade-off is visible. | Implemented |
| 55 | Documentation drift is guarded by tests | `tests/phase7/test_docs_consistency.py` asserts every registered HTTP route appears in `docs/API.md`, every env-var-backed setting appears in README and `.env.example`, README quickstart commands reference real files, and the architecture status table lists all phases as implemented. Docs are part of the deliverable, so drift fails the suite like code drift would. | Implemented |

## Explicitly out of scope

- Real hotel reservations, payments or booking transactions.
- Any live Google Hotels integration, scraping or reverse-engineered endpoints.
- Docker, microservices, hosted databases or message queues.
- Claiming that mock prices, ratings or availability are verified live data.
